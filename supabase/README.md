# Supabase

## Set up a project (one time)

Everything below runs in your project's **SQL Editor** (Dashboard → SQL
Editor → New query). The editor runs as the database owner, so no secret key
ever has to leave the dashboard.

1. **Schema:** paste all of `migrations/20261126000000_init.sql` and run it.
   It creates every table, the row-level security policies, the sign-up
   trigger, `join_unit()` and `search_chunks()`.
2. **Your unit:** edit the marked values in `seed/create_unit.sql` and run
   it. It returns the unit's **join code**.
3. **Study material:** run the book's `.sql` load script generated by
   `tools/ingest/to_sql.py` for each précis, part by part in order (see
   `docs/CONTENT.md`). These
   files contain précis text, so they are shared privately and never committed.
4. **ANO account:** the ANO creates an account in the app and confirms their
   email. Then run the `update profiles … role = 'ano'` statement at the bottom
   of `seed/create_unit.sql` with their email address.
5. **Confirmation links:** Authentication → URL Configuration → add
   `app.phoenixcadet.phoenix://login-callback` under **Redirect URLs** (and
   set it as the **Site URL**). Otherwise the email link opens
   `localhost:3000` (the email still gets confirmed; the cadet then signs in
   by hand).
5. **Cadets** create accounts in the app and enter the join code.
6. **Question review and Ustaad tables:** run
   `migrations/20261126010000_review_and_ustaad.sql`.

## Hosted tests and roles

Run `migrations/20261127010000_hosted_tests.sql`. It adds `submit_attempt()`,
which marks a cadet's answers on the server and allows one attempt per test,
and makes attempts read-only for cadets so a score can't be edited from the
phone. The ANO and senior cadets create tests from approved questions in the
Command Center; the ANO changes ranks and roles from the Cadets tab.

Check it locally: `psql -d phoenix_check -f migrations/20261127010000_hosted_tests.sql -f tests/hosted_tests_check.sql`.

## Précis figures

1. Run `migrations/20261127000000_figures.sql` (creates the `figures` table
   and the private `precis-figures` bucket, readable only by unit members).
2. Run the figures list generated by `python3 tools/ingest/figures.py sql`
   (`content/build/figures.sql`).
3. Storage → `precis-figures` → upload the two folders from
   `precis-figures.zip` (`army_sd_sw_2025/`, `common_sd_sw_2025/`) at the
   top level of the bucket, keeping the folder names. Figures not uploaded
   yet show a placeholder in the app.

## Turn on Ustaad (free, with Gemini)

1. Get a free API key at **aistudio.google.com** → *Get API key* (no card
   needed). Free-tier prompts may be used by Google to improve its products;
   a paid key turns that off.
2. In Supabase: **Edge Functions → Secrets** → add `GEMINI_API_KEY` with that
   key. Optional: `LLM_MODEL` (default `gemini-3.5-flash-lite`) and
   `USTAAD_DAILY_LIMIT` (default 50 questions per cadet per day).
3. **Edge Functions → Deploy a new function → Via editor**, name it
   `ustaad`, and create two files with the contents of
   `functions/ustaad/index.ts` and `functions/ustaad/core.ts`. Deploy.
   (With the Supabase CLI instead: `supabase functions deploy ustaad`.)
4. Keep **Verify JWT** on: only signed-in members can ask, and Ustaad reads
   the précis with the cadet's own permissions.

To use Claude instead, set `LLM_PROVIDER=anthropic` and `ANTHROPIC_API_KEY`.
Tests for the function: `deno test supabase/functions/ustaad/core_test.ts`.

Run the app against the project:

```bash
cd app
flutter run --dart-define=SUPABASE_URL=https://YOUR-PROJECT.supabase.co --dart-define=SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

The publishable key is safe to ship in the app; row-level security decides
what each signed-in user can read and write. Never put the secret
(`service_role`) key in the app or in this repository.

## Checking the row-level security rules

`tests/` runs the migration against a plain Postgres 16 with pgvector,
stubbing the parts of Supabase's `auth` schema it uses, then plays through a
cadet, a senior cadet, the ANO, a cadet from another unit and an anonymous
visitor. Each step prints what to expect next to the real result.

```bash
createdb phoenix_check
psql -d phoenix_check -v ON_ERROR_STOP=1 -f tests/00_auth_stub.sql -f migrations/20261126000000_init.sql
psql -d phoenix_check -f ../content/build/army_jd_jw_2025.sql   # optional: précis content
psql -d phoenix_check -f tests/rls_check.sql
psql -d phoenix_check -f migrations/20261126010000_review_and_ustaad.sql -f tests/review_check.sql
```

Some steps are meant to fail (for example a cadet trying to post an
announcement or promote themselves); the expected error is noted above each one.
